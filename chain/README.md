# chain/

| Path | Content | Committed |
| --- | --- | --- |
| `deployer/intent.toml` | op-deployer intent (addresses and parameters only), written by `make intent` | yes, after review |
| `deployer/state.json` | op-deployer deployment record, written by `make deploy-l1` | yes, as a record (the on-chain snapshot is the authority) |
| `out/genesis.json` | L2 genesis for op-reth | yes |
| `out/rollup.json` | rollup configuration for op-node | yes |
| `out/l1-addresses.json` | L1 contract addresses of this chain | yes |
| `out/chain-record.json` | genesis hash, L1 anchor, rollup config hash, key addresses | yes |
| `out/deployment.json` | deployer, L1 block range, measured cost | yes |

Both hosts mount `chain/out/` read-only at `/chain`. Host B receives a copy of this
directory after `make export` on host A (it is part of the repository, so `git pull`
suffices once committed).

Chain parameters (`CHAIN_ID`, names, L1 ids) are in the repository root `.env`. The intent
is generated by `op-deployer init` for the pinned release and then patched by
`scripts/render-intent.sh`; it is not hand-written, so field names always match the
release in use.
